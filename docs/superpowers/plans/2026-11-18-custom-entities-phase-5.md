# Custom entities, phase 5: camera

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Every implementer and reviewer runs on Opus 5.5.

**Goal:** A definition can be a camera: it takes pictures from an existing Home Assistant camera, draws rectangles and text on them, and shows the result as a new camera entity (still picture and Home Assistant's low-rate stream), built with nodes or with a C# class.

**Architecture:** A camera is the tenth row of the four domain tables, with no state and no commands. It holds a *current frame*; a frame is shown by a class (`Show`, or by answering `Frame()`) or by a graph's *Show frame* step, and Home Assistant pulls it through one new manager call that returns JPEG bytes. One frame is made per interval however many viewers there are, and nothing runs when nobody looks. `SharpImage` is a JPEG plus a list of drawings, decoded and encoded only when a picture is asked for, by the libjpeg-turbo library the Home Assistant image ships (P/Invoke from HassSharp); text is rasterised by StbTrueTypeSharp from an embedded DejaVu Sans.

**Tech Stack:** C# (.NET 11; P/Invoke to system `libturbojpeg`; one new package, `StbTrueTypeSharp`), Python (Home Assistant 2026.11 camera platform), SolidJS + Vitest (panel).

**Spec:** `docs/superpowers/specs/2026-11-17-custom-entities-design.md` (decisions 5 and 7 as amended on 2026-11-18, "C# API", "Catalog", "Bridge", "Python"). **Spikes:** `docs/superpowers/plans/2026-11-18-custom-entities-phase-5-spike.md` (both; the Home Assistant camera contract and the libjpeg-turbo handling rules are there) and rules 15 and 16 of `docs/superpowers/plans/2026-11-17-custom-entities-phase-1-spike.md` (the camera entity; bytes through Python.NET). **Code map:** `docs/superpowers/plans/2026-11-18-custom-entities-phase-5-map.md` — every task reads the sections its dispatch names. ## Decisions taken for this phase

1. **Imaging (the user's, 2026-11-18).** libjpeg-turbo from the system, no fallback codec; DejaVu Sans 2.37 embedded for text; the project is MIT-licensed. Only functions present since libjpeg-turbo 2.0 are called (`tjInitDecompress`, `tjDecompressHeader3`, `tjDecompress2`, `tjInitCompress`, `tjCompress2`, `tjFree`, `tjDestroy`, `tjGetErrorStr2`, `tjGetErrorCode`), so Ubuntu's 2.1 and the image's 3.1 both work.
2. **`SharpImage` is a JPEG and a list of drawings.** `Load` keeps the bytes; `DrawRect` and `DrawText` add to the list and return the same image; `ToJpeg` decodes, draws and encodes once — and returns the bytes it was loaded from when nothing was drawn, so a camera that only passes a picture on needs no codec. On a wire of a graph an image is copied (the bytes shared, the list copied), so a step never changes a picture another step holds. No resize: Home Assistant scales a still picture itself when a size is asked for.
3. **A camera has a current frame.** It is set by `Show` (class) or *Show frame* (graph), from any flow. A camera may also say how a frame is made when one is needed — a class by overriding `Frame()` or setting `OnFrame`, a graph by a *When a frame is needed* root — and then nothing runs while nobody looks. A frame request is not a command: it returns a value, has no service, and is not in the row's `commands`.
4. **One frame per interval.** Requests for one camera share the frame being made; a request that arrives within 0.8 × the camera's interval of the start of the last one made gets that frame again. Making a frame is limited to 8 s (Home Assistant gives up at 10 s). When making a frame fails, the last good frame is given for up to 30 s; after that, and when there has never been one, the request fails and Home Assistant shows no picture. Failures are logged once per reason, with one line on recovery, as a polled device's are. A viewer that leaves does not cancel a frame being made; stopping the definition does.
5. **The row.** `camera`: `state: {}`, `commands: {}`, one option `frame_interval` (number, seconds, 0.5–60, default 1; label "Seconds between frames"; description "How often Home Assistant asks for a new picture while someone is watching; 1 when left empty."). No `is_streaming`: the entity's state stays Home Assistant's `idle`.
6. **Pictures from an existing camera** come through Home Assistant's `camera.async_get_image` (10 s), JPEG only. A definition cannot take a picture of one of its own cameras (it would wait for itself): refused at once with a message that says so. Two definitions that photograph each other time out; not guarded.
7. **Entity definitions only.** *Take a picture*, *Draw rectangle*, *Draw text*, *Show frame* and *When a frame is needed* have `documents: ["entity"]`: no automation step takes an image yet (the design had them in automations too). The type `image` is not listed where a type is chosen (Constant, Convert, loops).
8. **Limits.** A picture is at most 20 MiB and 40 megapixels; an image carries at most 500 drawings; a text at most 200 characters, size 8–200 px (default 16); a rectangle's line 1–50 px (default 2). Outside these: a plain `ArgumentException` naming the limit. Drawing outside the picture is clipped, never an error. JPEG quality is 80.
9. **Colours** are named: Red (default), Green, Blue, Yellow, Orange, White, Black. `SharpColor` has these as static members and `FromRgb(byte, byte, byte)`; a graph step chooses a name.
10. **Not built in this phase:** a stream source (RTSP/HLS), recording, the `streaming` state, resizing, PNG, shapes other than rectangles, detection, a thumbnail on the definition's card, images in automations, the release-size assertion the design asked for (the dependency is one small managed library and a 0.76 MB font; `scripts/package_release.py` already refuses a package over 100 MiB).

## Review Focus

1. The source camera is off, slow or gone while someone is watching: the picture stays (the last good frame) for up to 30 s, the log gets one line per new reason and one on recovery, no runs pile up, and the camera recovers by itself. — Tasks 3, 6.
2. Three dashboards show the same camera, then all close: one frame is made per interval while they watch, none after. — Tasks 3, 4.
3. A damaged, truncated or enormous JPEG arrives from a camera: a plain error (or the usable part of the picture), never a crash of Home Assistant; the next frame works. — Task 2.
4. A definition is saved, turned off or deleted while a frame is being made or a picture is being fetched: cancelled, the new revision serves frames, nothing leaks. — Tasks 3, 6.
5. libjpeg-turbo is missing: the definition starts, a camera that only passes pictures on works, drawing fails with one plain line in the log that names the library. — Tasks 2, 3.

## Outcome of phase 5, and what it hands on

Phase 5 ended at `b5ebb11` (14 commits after `23cc01a`: Tasks 1–7 with three fix rounds, one fix wave after the whole-phase review and one follow-up to it; Task 8 was the build, the live check and the walk-through). All five suites pass (runtime 531 PASS lines with no compiler warnings, editor 22, host Python 191 with 55 skipped, packaging 7, frontend 1811); in the Home Assistant 2026.11.1 container the Python suite passes with none skipped (203) and both packaging smokes pass, the entity bridge smoke taking a picture through the real assembly on Alpine, musl and ARM64. A scripted live check against a real Home Assistant and a walk-through in the browser passed: a class camera that fetches a mock source and a camera built from nodes alone (When a frame is needed, Take a picture, Draw rectangle, Draw text, Show frame) both stream in a dashboard card; three viewers of one camera cost one frame per interval, and nothing is made once nobody watches; a source that fails or stalls leaves the last picture up and recovers by itself, with one log line per reason; a damaged or oversized picture is refused in plain words; a definition cannot photograph its own camera; a save, a restart, turning off and on, and delete and re-create leave one entity and no picture bytes in any log, trace or stored file.

Where the text above differs from what was built, this section is right:

- **Decision 4, the frame a camera has.** The last good frame is kept for the longer of 30 s and twice the camera's interval; a failed attempt is reused for at most 1 s. A frame that cannot be encoded (a damaged picture, one over 40 megapixels, drawn on) counts as a failure to make a frame: the last frame that did encode is answered for that time. A new revision takes over a copy of each camera's current frame from the revision it replaces and answers it while it starts; the revision being replaced answers with its frame while it stops (a camera that makes no frames answers its frame however old), and when it leaves the directory the new revision takes its place there at once, so no request across a save is refused. Once running, the first request makes a new frame, so a saved change shows at once. Home Assistant or HassSharp stopping is not logged as a failure to make a frame.
- **Decision 4, a frame that takes too long.** "The next request starts a new one" holds once the slow frame has ended. While a `Frame()` that passed its 8 s limit still runs, no second one starts and requests get the timed-out outcome; a `Frame()` that never ends leaves its camera without new frames until the definition is saved or reloaded. A graph's frame flow is cancelled at the limit (recorded Cancelled, "Took longer than 8 s", when history is on), so a Show frame after the limit never runs; class code cannot be cancelled.
- **The frame request in a graph.** It is its own root, *When a frame is needed* (`camera_frame`), with a *Show frame* step (`show_frame`), not the command `frame`. Show frame sets the camera's current frame whenever it runs, in a frame flow or any other; a flow that ends without it (a branch that decides not to, a wired *on error*) keeps the current picture, with no time limit. The image type and the five steps are for entity definitions only (`documents: ["entity"]`).
- **Decision 8, positions.** A position or size of a drawing step that is not whole is rounded to the nearest pixel, typed or wired; only a value that is not a number, or beyond ±1,000,000,000, fails. A control character in Draw text's text is drawn as a space.
- **A JPEG that ends before its size.** The header is read with a fresh decompressor, so such a picture is refused in plain words instead of taking the size of the picture decoded before it on that thread (libjpeg-turbo 3 answered success with the stale size).
- **Pixel buffers.** `SharpImage` rents from a pool of its own (buffers up to 16 MiB, two per size, about 64 MiB at worst across sizes) and allocates larger ones outright, so memory kept after viewing is bounded and not per thread.
- **Not built** (as decision 10 lists, and): the release-size assertion, a streaming state (a camera's state reads Idle while it streams), resizing.
- **Names and places.** `InvocationCause.Frame` (label "Frame needed") was added for frame runs; the graph camera's tests live in `tests/Runtime/EntityGraphTests.cs`; `TurboJpeg` carries test hooks (`Disabled`, `Progressive`, `ThreadHandles`); unlisted built-in types are decided by their catalog entry (`VisualCatalogSnapshot.Unlisted`), in C# as in the editor; in an entity definition a run is titled by its root step's label, not the generated method name.
- **Licences.** `LICENSE` is MIT, "Copyright (c) 2025-2026 Domagoj Zivanovic" (the holder line is the git author's name; to be confirmed). StbTrueTypeSharp declares "Unlicense OR MIT" and ships no licence file; its notice says so and carries the Unlicense text, with no holder line. The packager refuses a tree without either file of `licenses/`.
