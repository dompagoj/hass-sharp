# Vision: face and person detection (Project A) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A definition can add a **People detector** device for a camera and get, with nobody watching the camera, Home Assistant entities for whether a face or a person is in view, how many and when one was last seen, plus an annotated camera. A graph camera can place **Detect faces** between Camera frame and its Image. Both run on one Rust/tract library (YuNet for faces, YOLOX-nano for people) that is downloaded once when a definition sets up. Library nodes get a `[NodeSetup]` hook for that one-time work, and `SharpImage` gets `DrawCircle`.

**Architecture:** Bottom-up, every commit green, in two repositories (owner's decision of 2026-11-22, `.superpowers/sdd/2026-11-22-vision/split-decisions.md`). - **Spike facts that bind** (tract 0.23.10). Both models load with `tract_onnx::onnx().with_ignore_output_shapes(true).with_ignore_value_info(true)` and then get their input fact fixed. Input is 1×3×H×W **BGR** float 0–255 with no mean, scale or std, the picture at the top-left, H and W multiples of 32 (non-square allowed).
  - **YuNet:** padded with 0. Outputs by name `cls_8, cls_16, cls_32, obj_8, obj_16, obj_32, bbox_8, bbox_16, bbox_32, kps_8, kps_16, kps_32`. Score = sqrt(clamp(cls)·clamp(obj)), decoded as OpenCV's `FaceDetectorYN`. NMS IoU 0.3.
  - **YOLOX-nano:** padded with **114**. One output `[1, N, 85]`, each anchor `(dx, dy, lw, lh, obj, 80 class scores)`. Strides 8, 16 and 32 in that order, each grid row-major, with no +0.5 offset: `cx = (dx + gx)·s`, `cy = (dy + gy)·s`, `w = exp(lw)·s`, `h = exp(lh)·s`. Score = obj · cls[0] (person). Default threshold 0.45, NMS IoU 0.45.

Also `internal static void ImagePainter.Circle(Span<byte> rgb, int width, int height, int x, int y, int radius, SharpColor color, bool filled, int thickness)`.

**Behaviour:**
- A pixel (px, py) is painted when `d² = (px−x)² + (py−y)² ≤ r²`. For an outline it must also have `d² > (r − thickness)²`: the line is drawn inwards, as a rectangle's is, and `thickness ≥ radius` gives a disc. The math is in `long`, and only the box `[x−r, x+r] × [y−r, y+r]` clamped to the picture is visited, so a centre at `int.MinValue`/`int.MaxValue` neither overflows nor loops.
- Refusals throw `ArgumentException`: a radius outside 1–4096 → `A circle's radius is 1 to 4096 pixels`; a thickness outside 1–50 → `A circle's line is 1 to 50 pixels thick`; the 501st drawing → the existing `An image carries at most 500 drawings`. A refused circle is not added.
- The `SharpImage` class summary names `DrawCircle` beside `DrawRect` and `DrawText`.

**Interfaces:**
- Produces:
  - `[AttributeUsage(AttributeTargets.Method, AllowMultiple = false, Inherited = false)] public sealed class NodeSetupAttribute : Attribute`. Its summary: runs once when an entity definition whose graph uses any `[Node]` of the class starts.
  - `public sealed class NodeSetupContext` with:
    - `public SharpFiles Files { get; }`
    - `public void Log(string message, PyLogLevel level = PyLogLevel.Info)`
    - `public string RuntimeIdentifier { get; }`: `RuntimeInformation.RuntimeIdentifier` unless the constructor is given one
    - `public CancellationToken Stopping { get; }`
    - `public T Own<T>(T disposable) where T : IDisposable`, which returns its argument

    Its constructor is `internal NodeSetupContext(SharpFiles files, Action<string, PyLogLevel> log, CancellationToken stopping, Action<IDisposable> own, string? runtimeIdentifier = null)`. It takes no host type, so Task 9's tests can make one.
  - `public sealed record NodeSetupDescriptor(string Class, string InvocationType, string MethodName)`. `Class` is the containing type's name as messages give it (`FaceDetection`; a nested type is `Outer.Inner`). `InvocationType` is written as `NodeMethodDescriptor.InvocationType` writes it.
  - `NodeMethodDescriptor.Setup : NodeSetupDescriptor? { get; init; }`: the setup of the method's own containing type (not a base type's). It is null when there is none, and for every Custom C# node.
  - Generated only for a graph that uses such a method: `public static class SharpNodeSetups { public static readonly (string Class, global::System.Func<global::HassSharp.NodeSetupContext, global::System.Threading.Tasks.Task> Setup)[] All = [ ... ]; }`. It has one entry per class, ordered by `InvocationType` ordinally, and each entry is a `Section` of the first node that uses it.

**Behaviour:**
- **Signature.** A `[NodeSetup]` method is `public static`, non-generic, returns `System.Threading.Tasks.Task`, takes exactly one parameter of type `HassSharp.NodeSetupContext` (not ref, out or params), and sits in a type whose accessibility `ValidMethod`'s rules accept. Otherwise it is an error at its identifier: `A setup method is public static Task Setup(NodeSetupContext context): public, static, returning Task and taking one NodeSetupContext`.
- **A second `[NodeSetup]` in one type** is an error at the second: `A class has at most one [NodeSetup] method; this is its second`.
- **In a type with no `[Node]` method** it is a warning (severity 2): `[NodeSetup] runs for the [Node] methods of its class, and this class has none`.
- **In the code of a Custom C#, C# entity or C# device node** it is an error: `[NodeSetup] works in a node library only; move this class into one`.
- **Catalog.** Each library `[Node]` of a class with a setup gets `spec["documents"] = ["entity"]`, and nothing else changes. So the automation palette leaves it out (`FE/src/visual/graph.ts:58`). Both validators refuse it in an automation with code `node.document` and the existing `Words.WrongDocument` sentence, `Detect faces only works in the graph of an entity definition; delete it from this automation` (C# `VisualGraphValidator.cs:1107`, TS `contract.ts:1844`). No frontend change.
- **Generator.** `SharpNodeSetups` is emitted after `SharpNodes`, from the methods `MethodOf` finds for the graph's nodes. A graph with none gets the source it has today.

### Task 3: The host runs node setups and disposes what they own

**Files:**
- Modify:
  - `CC/HassSharp/Devices/DefinitionHost.cs`: `CompiledDefinition` at :13–40; `SetUpComponent`'s local `SetUp` at :213–226, which becomes a shared method; `StopCoreAsync`'s `finally` at :463–500
  - `CC/HassSharp/Devices/DefinitionHost.Graph.cs`: `PrepareGraph` at :55–75; `SetUpComponents`' `finally` at :171
  - `CC/HassSharp/Devices/EntityApi.cs`: `CompileDefinition` at :96–100, beside `NodeClasses` at :108
- Test: `tests/Runtime/NodeSetupTests.cs`

**Interfaces:**
- Consumes: `SharpNodeSetups.All` and `NodeSetupContext` (Task 2).
- Produces:
  - `internal sealed record NodeClassSetup(string Class, Func<NodeSetupContext, Task> Run);` and `CompiledDefinition.NodeSetups : IReadOnlyList<NodeClassSetup> { get; init; } = [];`. `EntityApi.CompileDefinition` sets it from `internal static IReadOnlyList<NodeClassSetup> NodeSetupsOf(Assembly assembly)`, which reads the `All` field and returns `[]` when the assembly has no `SharpNodeSetups`.
  - `DefinitionHost.Own(IDisposable disposable)` (internal): the object is held under `gate` until the definition stops. Once the list is released, `Own` disposes its argument at once and throws `ObjectDisposedException("{definition.Name} has stopped: it keeps nothing more")`.
  - A bounded-run helper replaces the local `SetUp`: `Task RunSetUp(Func<Task> work, string who, string what)`. It runs on a `LongRunning` thread, with `Within(task, clock)` on `setupClock`. A failure reads `{who}: {message}` and a time-out `{who}: {what} did not finish within {n} s`. Components call it with `what = "Setup()"`, so their sentences are unchanged.

**Behaviour:**
- `PrepareGraph` runs, in order:
  1. the graph's own entities;
  2. **each `NodeSetups` entry, in order**, with `who = "{definition.Name}: {Class}"`, `what = "its [NodeSetup]"` and `new NodeSetupContext(Files, Log, Stopping, Own)`;
  3. the C# nodes (`SetUpComponents`);
  4. the When started flow.

  Node setups and C# nodes share one `SetupClock` (`setupClock ??= new SetupClock()`), nulled in one `finally` around both. So a download's receiving stops the clock, and the When started flow still gets a clock of its own.
- A setup that throws fails the prepare with `{definition.Name}: {Class}: {message}`, and one past the limit with `{definition.Name}: {Class}: its [NodeSetup] did not finish within {n} s`. Nothing is registered with Home Assistant. What the setup owned so far is disposed when the failed host is stopped (the manager already stops it, `UserScript.ClearCoreAsync`).
- `StopCoreAsync`'s `finally`, after `downloads?.Close()`: under `gate`, take the owned list and set it empty (released is already true).   1. It waits for `video.NextFrameAsync(linked)`, where `linked` is `Stopping` plus `FrameTimeout`. A time-out throws `TimeoutException($"no frame from {Camera.EntityId} within {FrameTimeout.TotalSeconds:0.#} s")`, and a null frame (never for a camera) returns.
  2. On the unmodified frame (`using`): `faces = detector.Faces(frame, FaceInput, FaceScore)`, `people = detector.People(frame, PersonInput, PersonScore)`.
  3. It shows `Vision.DrawFaces(Vision.DrawPeople(frame.Copy(), people), faces)` on `camera`.
  4. It updates the entities with `now = DateTimeOffset.UtcNow`, the same way for faces and for people. An entity is set only when its value changes.
     - `faces`/`people` = the count.
     - With count > 0, `lastFace = now`.
     - **Seen** = `count > 0 || (lastFace != null && now − lastFace < StayOnFor)`. So with Stay on for 0 it is on only while the newest analysed frame has one, and a frame without one between two that have one never turns it off (anti-goal).
     - **`last_face_seen`** is set to `lastFace` when Face seen turns on; at most once every `LastSeenEvery` while it stays on; and to `lastFace` when it turns off (Ruling 15).
  - A check that fails (no frame in time, a detection error): `faces`/`people` become unavailable (`Available = false`) until a check works again, and each seen entity is recomputed with count 0, so it turns off once `StayOnFor` has passed since its last detection, never stuck on (Ruling 17). Then the exception is rethrown: `Every` logs each new reason once at Error and the recovery once (`{Name}: the timer callback every 500 ms failed: …`). The camera keeps its last frame. A check that works sets `faces`/`people` available again.
- **`Stop()`:** `await video.DisposeAsync()` when there is one, `detector?.Dispose()`, then `Log("People detector stopped", PyLogLevel.Debug)`. It null-checks both, because Stop runs even when Start did not.

## Rulings

1. **`[NodeSetup]` classes are entity-only through the catalog's `documents`.** Both validators, the palette and the clipboard already read it. So "only in a custom entity definition" needs no new code path or message: the existing `node.document` sentence ("… only works in the graph of an entity definition; delete it from this automation") is used. Cost if wrong: a dedicated code and sentence later.
2. **The generated `SharpNodeSetups` lists only the classes the graph uses**, after `SharpNodes`, and only when there is one, so every existing graph's source stays byte-identical. Cost if wrong: none for pins; a different emitted shape is one method to rewrite.
3. **Setups run before the C# nodes, on their clock.** The spec says "on the same `SetupClock` as C# nodes' `Setup()`", and running them first lets a C# node use what a setup loaded. Cost if wrong: an order swap.
4. **`panic = "unwind"` with `catch_unwind`.** A tract panic under `abort` would kill Home Assistant, and the size gain is small. If the library is still over 8 MiB after Task 6's levers, Task 6 reports and the build goes on rather than stopping. Two models make 8 MiB harder than one did: YOLOX alone is 3.5 MiB of ONNX. (2026-11-22: the owner dropped `panic = "abort"` and NNEF from Task 6, which does levers (a)–(d) only.) Cost if wrong: a larger download.
5. **Both ONNX models are committed** (232 KB MIT and 3.6 MB Apache-2.0, each with its licence) rather than downloaded by the build, so Docker builds are offline and reproducible. They move with the crate to hass-sharp-vision's `native/model/` (Task 7).
6. **Fixtures.** `group.jpg` is the spike's Wikimedia photo (CC BY 2.0, Steve Evans), downscaled to 640×427. `street.jpg` is the Eighth Avenue photo (CC0), downscaled to 480×640. Both are attributed in `native/NOTICE`, the CC0 one too, and move with the crate. Commons carries a personality-rights notice for the people shown in the first. It is a test fixture, not shown in the product. Owner to confirm, or swap it for a public-domain photo (only the pinned counts change); Task 15 asks again before it becomes public.
7. **`DrawCircle(x, y, radius, color, filled = false, thickness = 2)`.** This is the spec's order with an outline's thickness added last, as `DrawRect` has it, and an outline by default, as a rectangle is. Radius 1–4096.
8. **Error sentences, entity names, icons and drawing colours** are this plan's (Tasks 2, 3, 10, 11); the spec left them to the builder. Person boxes are cyan, so they never read as a face's green.
9. **`input_size` is 64–1280 and a multiple of 32; at most 64 faces and 64 people a call; at most 4 cached plans per model.** This bounds memory and time per frame. A crowd of more than 64 counts as 64. Cost if wrong: constants.
10. **`NativeLibrary.Free` is never called.** The library stays loaded for the process, and each detector is closed on stop. Unloading a Rust `cdylib` with thread-locals is the riskier path.
11. **The vision tests compile `Vision.cs` directly** (a collectible context and a hand-made `NodeSetupContext`) as well as end to end, so concurrency and drawing limits can be tested without a camera.
12. **AGENTS.md gains one sentence, not a suite.** The cargo suite left with the crate, so hass-sharp's list of suites is as it was; the sentence warns that hass-sharp-vision's tests compile `tests/Runtime/` under the name `HassSharp.RuntimeTests`, so a change there can break them. Cost if wrong: one sentence to drop.
13. **`VisionDetector` has a finalizer that closes a detector never disposed.** A C# device's `Stop()` does not run when its definition fails to start after its `Setup()` succeeded, for example when a later C# node's `Setup()` throws (`DefinitionHost.StopCoreAsync` returns at `start == null`). The People detector's detector would then leak until the process ends (anti-goal). The finalizer closes it when its load context is collected; nothing calls it concurrently, because by then nothing reaches it. `[NodeSetup]`'s `Own` is disposed on every stop and needs no backstop.
14. **`PeopleDetector`'s `Setup`, `Start` and `Stop` are `sealed`.** A derived class that forgot `base.Stop()` would leak a detector and an ffmpeg reader. A derived class can still add entities in its constructor. Cost if wrong: unsealing them later is compatible.
15. **Last seen is not written on every check.** Writing it at 2 Hz while someone stands at the door would put two state changes a second into the recorder and logbook. It is written when the seen entity turns on, at most once a minute while it stays on, and at the last detection's time when it turns off, so its final value is always the last time one was seen. Cost if wrong: one constant, or always writing.
16. **Seen and count entities are not restored; last seen is.** A restored "on" with no detection in memory would turn off at the first check anyway. Until the first check, they are unknown.
17. **Each check waits at most 10 s for a frame** (`FrameTimeout`). `NextFrameAsync` otherwise waits until a frame comes, and `Every` runs one call at a time, so one stalled camera would stop all later checks silently. A check that fails makes the counts unavailable and lets each seen entity expire on its hold time, so a camera that drops out while Person seen is on never leaves it stuck on (controller's ruling, refining the spec's "leaves the entities as they were": a stuck occupancy sensor misleads automations more than a missed one).
18. **The setting bounds are this plan's.** Scores are 0.1–1, because a score of 0 decodes every anchor. Check every 0.1–60 and Stay on for 0–3600 are the spec's.
19. **The device's frames come from the fake ffmpeg**, with a `still=` option added (Task 9, in hass-sharp: it is a generic test helper), rather than from a real ffmpeg. Neither repository's tests have needed ffmpeg on the host, and switching a file's frame on and off is deterministic where a real clip's timing is not.
20. **The Camera setting is a `CameraEntity`.** HassSharp forwards its own camera platform (`const.py` `PLATFORMS`), so the camera domain is always among Home Assistant's entity domains. But `PeopleDetector.cs` compiles only once Home Assistant's entity classes have arrived, as `EntityStartupTests`' `LampPlug` does. On a first start before they arrive, its definitions fail to compile and start by themselves once the classes come (`RetryFailedLoads`). Cost if wrong: an `Entity` setting with a domain check in `Setup()`.
21. **The split is the owner's** (2026-11-22, `split-decisions.md`): binaries are release assets of hass-sharp-vision, never committed; the crate, `Vision.cs`, `PeopleDetector.cs`, the example definition and the manifest live there; hass-sharp keeps `DrawCircle`, `[NodeSetup]`, Add external and generic test helpers. Tasks 1–6 were done before it and stay as written.
22. **hass-sharp-vision's C# test project compiles every file of hass-sharp's `tests/Runtime/`, under the assembly name `HassSharp.RuntimeTests`.** The helpers the vision tests need reach into each other (`NodeSetupTests` uses `VisualExecutionTests` statically, `EntityApiTests.Lit` calls `VisualExecutionTests.Lit`, `EntityHostTests` uses `RuntimeCoreTests` from `Program.cs`, `FakeFfmpeg` lives in `CameraFeedTests`), so a hand-picked list would break on any refactor there, and hass-sharp's `Program.cs` then serves as the runner, finding the vision suites by `[RuntimeSuite]`. The tests need internals (`CameraFeeds` limits, `DefinitionHost` timeouts, `NodeSetupContext`'s constructor), which hass-sharp gives only to `HassSharp.RuntimeTests` (`RuntimeTestAccess.cs`); borrowing the name needs no hass-sharp product change. The follow-up is a test kit for library authors (spec). Cost if wrong: the kit replaces it.
23. **The crate's history is moved with `git subtree split`, then rewritten under `native/` with `git filter-branch --index-filter`**, rather than merged in with `git subtree add`. A subtree merge keeps the carried commits with the crate at their trees' root, so `git log -- native/…` and `git blame` stop at the merge; rewritten, they reach Tasks 4–6's commits. Their hashes change; messages, authors and dates do not. `git filter-repo` is not installed, and nothing is installed on the host. Cost if wrong: a merge commit instead.
24. **The pins are a local build's until the first release, and the release's after.** Only the release workflow publishes binaries (split decision 1), so before it exists there is nothing to pin from; a full local `build.sh` run gives real checksums for the tests and Task 14's host-served check. Builds of the same source in the same image are usually bit-for-bit the same, but nothing relies on it: the release compares and says, and Task 15 pins the release's when they differ. Cost if wrong: one extra pin commit.
25. **CI's C# job is switched off by `HASS_SHARP_REF: none` in the workflow, step by step, and passes with a notice** (split decision 5 allows failing or gating). A job that failed on every push until hass-sharp's branch is on GitHub would hide real failures of the other job. It pins a sha, not a branch, so hass-sharp changes reach this repository only through a commit here. Cost if wrong: one `if:` per step.
26. **Every release carries `NOTICE` and `THIRD-PARTY-LICENSES` beside the binaries** (carried from Task 4's review). The MIT, Apache-2.0 and Zlib licences of the linked crates ask for their texts with a binary, and the release is how the binary is distributed; the models' licences go in the same file. The texts are made with `cargo-about` inside Docker and checked current by CI. Cost if wrong: two fewer assets.
27. **The release builds each RID on a runner of its own architecture** (`ubuntu-24.04`, `ubuntu-24.04-arm`, free for public repositories). An arm64 tract build with fat LTO under QEMU would take many times longer; only the optional arm RIDs run emulated. Cost if wrong: one runner and a QEMU step.
28. **hass-sharp-vision's layout is `native/` for the crate and `nodes/` for the node libraries and the example definition**, so its manifest's paths are `nodes/Vision.cs`, `nodes/PeopleDetector.cs` and `nodes/front_door_people.json` (spec §6). Cost if wrong: three paths.
29. **The branch is rebuilt by cherry-picking onto `8819664`**, not by an interactive rebase (not available here). The commits kept are exactly those that touch nothing under `nodes/`, and the result is checked against the backup tag (Review Focus 7). Cost if wrong: none; the tag holds the old tip.
