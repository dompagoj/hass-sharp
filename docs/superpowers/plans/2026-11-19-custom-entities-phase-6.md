# Custom entities, phase 6: MCP tools and docs

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Every implementer and reviewer runs on Opus 5.5.

**Goal:** An assistant connected over MCP can build, change, run and inspect entity definitions as it can automations, and a person can learn the whole feature from the docs.

**Architecture:** The MCP adapter (`llm.py`) gains one tool per entity operation, named `entities_*`, each a thin call to the entity API the panel already uses; nothing about definitions is added to the automation tools except a `document` choice on the two catalog tools. The entity API gains the two things an assistant needs and the panel did not: running a Trigger step now, and working out a Custom C# node's pins from its code. Complete, validated example definitions ship in `authoring_examples.json`. The docs get one guide, `docs/custom-entities.md`, and the existing guides say where definitions touch them.

**Tech Stack:** Python (Home Assistant 2026.11 `llm` API, `probatio` schemas), C# (.NET 11), SolidJS + Vitest (two panel leftovers), Markdown.

**Spec:** `docs/superpowers/specs/2026-11-17-custom-entities-design.md` ("Bridge": `EntityRequest(json)` "(list, read, preview, save, delete, set_enabled, types, run)"; "Python": "`llm.py`: `entities_*` MCP tools in `SPECS` and `_call`"; phase list item 6). **Code map:** `docs/superpowers/plans/2026-11-19-custom-entities-phase-6-map.md` — every task reads the sections its dispatch names; section 3 is the list of everything earlier phases handed to this one. Hand-offs: "For phase 6" at the end of the phase 2, 3, 4 and 5 plans.

## Decisions taken for this phase

1. **Nine tools, named as the design says.** `entities_types`, `entities_list`, `entities_read`, `entities_preview`, `entities_save`, `entities_set_enabled`, `entities_delete`, `entities_run`, `entities_history` (26 tools in all; 16 read-only). `trace` serves both kinds as it is (a run is found by its id). No `kind` parameter on the automation tools: a wrong guess there would edit the wrong document.
2. **The catalog tools take `document`.** `get_capabilities` and `get_node_schema` gain an optional `document`: `"automation"` (the default, today's answer) or `"entity"`. With `"entity"` the catalog holds the node kinds a definition may use (those whose `documents` is absent or lists `entity`), the examples are the example definitions, and the rules gain a `definitions` entry. `get_node_schema` for `entity_state`, `set_entity_state` and `entity_command` also returns `entityDomains` (their ports come from the entity's type), whatever `document` says.
3. **`entities_run` runs a Trigger step now**, as `run` does for an automation: `{id, triggerId}` → `{runId}`. It needs the definition on and its saved revision the one running; the run is recorded whatever the step's history setting, so its trace can be read. Nothing else is run by hand: a command is sent by calling the entity's service in Home Assistant, a State follows its sources, setup and frames run when the definition starts and when a camera is watched.
4. **Custom C# steps in a definition.** `EntityRequest` takes `deriveSignatures: true` on `preview` and `save`, as `VisualRequest` does: each Custom C# node's pins are first written from its code. With it, `preview` also answers `graph` — the graph with those pins, and nothing else of the definition (no settings come back). The MCP tools always pass it; the panel does not and is unchanged.
5. **`entities_list` is a summary**: per definition `id, name, revision, enabled, status` (`running`, `setup`, `failed`, `off`), `activationError`, `logic` (`"graph"`, or the class's type id), `device` (true or false), `entities [{key, domain, name, entityId}]` (the entity id Home Assistant gave it, or null) and `triggers` (as `list` gives for an automation, so `entities_run` has its ids). `entities_read` is the whole document, without node sizes.
6. **The definition schema is strict at the top and open below.** `{name, device?, settings?, entities?, logic}` with `logic` either `{kind: "graph", graph: GRAPH}` or `{kind: "class", type}`; anything else at those levels is refused by the schema. What is inside `device`, a setting or an entity is checked by the server, which answers in words. `device.via` (`{definition}` or `{deviceId}`) is documented for the tools.
7. **Secrets through MCP.** The server already masks every answer; the adapter also refuses to pass on an answer in which a setting marked secret carries a value. The tools say how to send one back: unchanged (`value: null, hasValue: true`) keeps the stored value; a new `value` replaces it; `value: null` without `hasValue` clears it. The docs say that a secret typed into a conversation reaches the assistant's provider, and that the panel is the place to enter one.
8. **Example definitions** live in `ex` under a new key `definitions` — `[{title, description, definition, library?}]` — and are returned only for `document: "entity"`. Five: *Motion in either room* (the acceptance case: two **Has state** → **Or** → **State**); *Plug over HTTP* (a setting for the address, a Trigger every 10 s → HTTP request → Get field → Set state for a switch and a power sensor; **When commanded** turn on and turn off → HTTP request); *Camera with a box* (the five camera steps); *File at setup* (**When started** → Download file → Log; the address and checksum are placeholders and the description says so); *Plug from a class* (a `SharpDevice` class in a library source, with a `[Setting]`, and the definition that uses it). Each previews with no diagnostics, pinned by a test.
9. **Docs layout.** `docs/custom-entities.md` is the guide (what a definition is; the derived sensor step by step in the panel; entity types with their state values, commands and options; State, When commanded, Trigger and When started; settings and secrets; devices; HTTP, downloads and restore; cameras; classes; run history; limits and behaviour worth knowing; through MCP). `docs/node-libraries.md` gains a short section on entity classes that links there. `docs/mcp-authoring.md` gains the nine tools in its workflow and contract. `README.md` names the third page and the guide. `docs/backend/entity-definitions.md` is the API reference (`hass_sharp/entities` operations and the document), in the manner of `docs/backend/visual-automations.md`. The complete class example in the guide is the `ex` example's source, word for word, pinned by a test.
10. **Leftovers taken**: `CameraSnapshot(entityId, CancellationToken)`; the refusal a frame-making camera can still meet at the instant a save stops it (`|| replacing`); **Run now** on a Trigger step in a definition's editor; a **Part of** choice in the device form (`via`); the Trigger step's description inside a definition; the stored-state warning's wording; a camera named by its name in log lines; `command.unhandled` naming the entity by name as well as key. **Not taken** (stay where they are listed): a save-time warning for a definition that photographs its own camera, everything marked "Not tied to a phase", the guide design.

## Review Focus

1. An automation and a definition share an id (`porch`): each tool reaches its own; `history` shows only the automation's runs and `entities_history` only the definition's; deleting one leaves the other. — Tasks 1, 3.
2. A definition with a secret setting goes through every tool: the value is in no result; a save that sends the masked setting back keeps the stored value; a save without `hasValue` clears it; a library save that rebuilds the definition answers without it. — Task 3.
3. An assistant sends something ordinary and wrong — an automation graph to `entities_save`, a definition to `save`, an entity-only step in an automation, a `definition` key inside the graph, an unknown entity type, a class type that does not exist, `new` as an id: refused with a sentence that says what to send, never `internal`. — Tasks 1, 3.
4. The MCP server is in read-only mode, or the user is not an administrator: none of the four mutating entity tools is offered or callable. — Task 3.
5. `entities_run` on a definition that is off, failed, being replaced, or whose step is not a Trigger: a plain refusal; on a working one, a run id whose trace reads. — Tasks 1, 3.
